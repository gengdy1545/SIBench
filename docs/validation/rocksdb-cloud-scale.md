# rocksdb-cloud 目标规模与对象回收

更新：2026-10-29。记录 rocksdb-cloud 的目标规模结果及边界。各运行的原始配置、身份、日志和结果保留在独立目录；未结束的运行不标为通过。单次样本不支持后端性能排名；数据文件 Rewrite / 索引版本 GC 尚未实现。

## 输入、构建与比较条件

- YCSB 87m：`ycsb-87m-n22/trace`，Baseline 87,060,000 操作、workload 29,927,464 操作、25,567,761 查询。
- sysbench 87m：`sysbench-87m-sl16/trace-current`，Baseline 174,120,000 操作、workload 22,677,104 操作、12,708,328 查询。
- 以上两份同机后端对照使用 jar `fc8c718ab475050c7ac7e1d33487234ac87a482048c7c01e8605a8d4c973d39c`、JNI `6ac08918ea930fd6cec85b6f939d5577dd857477057896e1bdc9733a27e24353`。本地 RocksDB 与 rocksdb-cloud 的引擎基线均为 9.1.1。该构建包含分块响应，尚无后续 Baseline 批量写和 index manifest；与新构建的加载速率不能直接拼接比较。
- 每个后端新建索引，gRPC、64 client、operation、二级开启、row_id、4,096 在途、120 s 请求超时、完整发布及逐查询 SHA-256 校验。预检会读取输入，页缓存未强制清冷，索引与 JVM 为新建；COS / 本地 S3 保留本地 SST，workload 查询不等于远端随机读。
- 同机按后端顺序运行，使用相同输入和资源；YCSB 在 `sibench_6`，sysbench 在 `sibench_7`，两台机器之间的 wall 不作版本收益对照。后端前台响应、Flush 和后台 compaction 分开报告。
- 有效配置与完整身份见各目录 `identity.sha256`、`replay.yaml`、`<backend>/index.yaml`；对象存储 profile 为 `config/storage.yaml` 的 COS 内网域名或本地 SeaweedFS。凭据只通过环境传入。

运行目录 `sibench_5:/data/sibench/results/poc/p1-hybench-cloud-final-3-20261028/`，COS 独立前缀 `sibench/p1-hybench-cloud-final-3-20261028`。16 GiB 服务堆与 16 GiB 驱动堆；setup 600 s、replay 最多 6 h、成功后 120 s 空闲观测、teardown 30 s。以非 root 的 `sibench`（UID 1000）运行。该 120 s 配置运行失败；600 s 配置的成功另列，不改写该失败。最先失败是 dispatch 19,996,565、client 17、源事件 49,320,341 的非事务查询超过 120 s；驱动 wall 26:51.64、exit 1。服务峰值 RSS 3.86 GB，32 个发布 worker 空闲，查询线程 53 个在 native seek；不能把它归因于旧版一次性物化结果的堆耗尽，也不能把后续停止等待当作首因。失败索引、bucket 控制文件、线程转储和日志已保留，先完成下述有界诊断，再按用户批准的保护期限运行新配置。

## 延迟观测补充

原 JNI 只有按类型的次数、失败数、字节和累计微秒数，无法恢复 p50 / p95 / p99。观测补充增加 32 桶的常量内存直方图：上界为 1、2、4…2^30 μs，最后一桶表示溢出，输出分位数为所在桶上界。成功和失败请求都纳入；零样本不解读分位数。

补充 jar `1042aeb821ce84d0f6f63247bbe72dcd02f240fafcbcee75b649dc9dcae5bd26`、JNI `5f0e1f5409c90313ddebcd2a62b367883abad3587c08573c927705a1d4eb87ec`。Java / JNI 必须配套重建；格式不匹配在打开索引时拒绝。并发后台请求使聚合字段不构成事务性快照，直方图单列 `samples`，分位数以这些样本计算。

根 Maven 与手算分桶 / 溢出的原生测试通过；短输入 COS 集成在 `sibench_4:.../p1-object-latency-2-20261028/` 通过，10,700 次逐查询摘要 / 0 不匹配，index manifest 已生成；同一索引重开与新本地目录的仅从 bucket 冷启动均通过：水位 2,900，各核对 9,700 个快照查询 / 0 不匹配，另有 1,000 个事务内查询按定义未核对。启动至 ready 的 1 s 采样耗时分别为 17.07 / 6.02 s（不是重复性能测量）。最终 Flush 的 64 个写请求全部有直方图样本，p50 桶上界 131,072 μs、p95 / p99 上界均为 2,097,152 μs，总写入 731,481,599 B、累计 20,037,312 μs。分位数包括 MANIFEST 与不同大小 SST 请求，不能把聚合分布称为固定大小 PUT 的延迟。观测构建的原生测试与必要构建身份保留；无研究价值的启动失败和重复构建日志已清理。观测补充不改变键、可见性、发布或请求语义；既有三来源完整正确性证据按这些未改变的边界复用，不为增加观测字段重跑长验收。目标规模旧运行的请求分位数为 N/A，不用短输入替代。

## Java / JNI 适配成本的有界分解

在 `sibench_4` 对同一短 Trace 已完整核对的本地 / COS 索引做只读微测（`p1-adapter-cost-20261029`）：两份原报告均为 10,700 次摘要 / 0 不匹配，期望文件 SHA-256 同为 `020b1982…`。本地复制原验证目录，云端复用已验证的冷启动目录，均由现有 reopen 支持，不重放写入或新增 checkpoint。两个存储给出的最小 / 最大原始键相同。

同一主机、JDK 17、4 GiB 堆、jar `1042aeb8…`，local / cloud 各两次交错、新 JVM；每次 8 轮，前 3 轮热身，后 5 轮每轮平均 ns/op 取中位数。每轮各 50,000 次游标创建 / 关闭和 500,000 次对固定真实末尾键的 seek；打开索引单独计时，不并入操作耗时。

| 操作 | 本地两次 ns/op | 薄 JNI 云路径两次 ns/op | 本地 Java 分配 B/op | 云路径 Java 分配 B/op |
| --- | ---: | ---: | ---: | ---: |
| 无界 cursor 创建 / 关闭 | 812 / 828 | 746 / 756 | 136 | 约 0 |
| 带上下界 cursor 创建 / 关闭 | 1,063 / 1,073 | 845 / 832 | 200 | 约 0 |
| 固定键热 seek | 995 / 1,010 | 742 / 733 | 约 0 | 约 0 |

`ThreadMXBean` 只统计本线程 Java 分配；此热循环中薄 JNI 的 Java 游标可被 JIT 消除，C++ 分配不在该计数内。真实查询调用栈可能有不同逃逸行为。RocksJava 每次查询建立的 `ReadOptions` / `Slice` / iterator 生命周期在这个微测里有可见成本，与短输入查询阶段的路径差异相容；不因此声称已唯一解释端到端差异。原生 fork / 编译、物理 SST 布局和缓存仍有差异，固定键热 seek 不是大范围扫描或远端随机读，微秒数不能相加外推服务吞吐。保留现有适配，不为该结果添加另一套查询语义或进一步优化。

## 引擎旧 SST 的延迟回收

`sibench_3`，本地 S3，证据：[回收目录](../../results/poc/p1-cloud-reclaim-20261028/)。短输入回放 10,700 次摘要 / 0 不匹配；保留服务，让默认 1 h 延迟删除器处理 compaction 替换的旧 SST。

- bucket 逻辑字节从 751,601,964 降至 235,827,553，减少 515,774,411 B（约 68.6%）；本地索引约 236 MB，没有随 bucket 的延迟删除而再缩小。请求计数只截至 workload 末 Flush，不覆盖此后的一小时延迟删除；不能用当时的 `delete=0` 否定后续实际回收。
- 首次下降约在 22:04，约 22:08 已到最终大小。延迟从对象成为过期文件并安排删除时算起，不能从 workload 结束时统一外推一小时。
- `bucket-size-sampled-2.txt` 与 `bucket-size.txt` 的有效采样相符；早期采样脚本误解析列导致的零值单独保留为 `bucket-size-sampled-misparsed.txt`，不用于回收结论。
- 27 次 flush、6 次 compaction 的 SST 输出为 311,183,588 / 440,411,846 B；workload 末 Flush 后没有观察到 compaction。这是自然 LSM compaction 产生的旧对象删除，未删逻辑保留版本，也未执行数据文件 Rewrite。

延迟回收结束后又在 `p1-cloud-reclaim-verify-20261028` 的全新本地目录只从同一 bucket 打开，水位 2,900，9,700 个快照查询逐查询摘要 / 0 不匹配，另有 1,000 个事务内查询不核对。这补证了删除旧 SST 后仍能恢复有效索引，不只是观察逻辑字节减少。原 jar / JNI 与回收实验一致，不重载 Baseline。
