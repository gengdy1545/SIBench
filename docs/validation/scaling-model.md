# 采集管线的扩展模型：SF10 实测推算 SF1000

2026-10-27。远程采集机固定为 32 CPU / 64 GB / 500 GB xfs（每来源一台），代码为当前 v9 / zstd 严格版本（new21 并行导出/核验、编译器分配优化 new24；旧明文、旧 `baseline.ops`、`locators.tsv` 与按会话跟踪兼容已删除）。

## 方法

各阶段按增长关系分两类，用 SF10 量级（每来源基线 8,706 万行）远程实测的耗时与体积线性外推，SF1000 量级取 100 倍行数：

- **随数据量增长**：静止库（装载与索引、统计信息）、首次导出与核验、基线 Parquet、编译的基线阶段、每次回放的基线加载、认证采集的行审计终态比对。按行数 × 100。
- **随回放预算增长**：原生执行、编译的负载阶段、原始采集、Trace。正式采集的目标是 `config/long_replay.yaml` 的 6.66 亿有效操作，与规模无关；倍数由 `plan-operations` 从同机最新的 5% 正式采集求得：HyBench × 9.30（TP / XP 各 56 min）、sysbench × 29.4、YCSB × 22.3。

线性外推是下界：数据远超内存后每次操作的代价、PG 外部排序（n log n）与带索引的装载都会更慢。

## 两点实测：870 万行与 8,706 万行

同一台远程机、同一并发（32）、同样的原生参数，只把基线行数降到十分之一（HyBench 为 SF1 对 SF10，TP / XP 各 6 min；sysbench、YCSB 为相同的事件数 / 操作数），各做一次完整核验采集（`hybench-sf1-c32`、`sysbench-8m-c32`、`ycsb-8m-c32`）。

| 阶段 | HyBench SF1 → SF10 | sysbench 8.7m → 87m | YCSB 8.7m → 87m |
| --- | --- | --- | --- |
| 静止库构建 | 73 s → 495 s（6.8×） | 28 s → 743 s（26×） | 91 s → 4,000 s（44×） |
| 静止库体积 | 2.2 → 21 GB | 5.0 → 49 GB | 20 → 132 GB |
| 首次导出 + 核验 | 20 s → 57 s | 11 s → 50 s | 116 s → 6,595 s（57×；new21 后 87m 约 2,476 s，约 21×） |
| 编译基线阶段 | 6.6 s → 60 s（9×） | 4.6 s → 36 s（7.8×） | 4.1 s → 30 s（7.3×） |
| 原生每次操作的代价 | 同样 781 s 内负载操作 5.62 亿 → 0.69 亿（8×） | 同样事件 483 s → 546–1,112 s（1.1–2.3×） | 同样操作，六个负载 154 s → 3,373 s（22×；范围扫描 36 s → 2,568 s，72×） |
| 编译负载阶段速率 | 25.5 万 → 24 万 ops/s（持平） | 209 s → 204–234 s（持平） | 666 s → 512 s（持平） |
| 原生执行中负载之外的时间 | 约 700 s（37 GB 追踪的会话审计） | — | 约 690 s → 590 s（负载之间的空档与会话审计，随追踪量） |

- 编译（负载阶段）只随操作数增长，与数据量无关：按回放预算线性推算成立。
- 原生执行每次操作的代价随数据量明显上升，越过内存时最陡：YCSB 870 万行的静止库 20 GB 放得进 64 GB 内存，8,706 万行的 132 GB 放不进，散列键的范围扫描变成随机读堆页。SF10 到 SF1000 全部在内存之外，所以上表按 SF10 每次操作代价推出的原生时间是下界，实际可能高出一个数量级。
- 随数据量增长的一次性阶段越过内存时超线性（静止库构建 26–44×；YCSB 首次导出在 new21 前 57×、之后约 21×），SF10 之后按线性推算同样是下界。

## 结论

- 随回放预算增长的编译、原始采集与 Trace 在 SF1000 下为小时级、数百 GB 以内。原生执行按 SF10 每次操作的代价推算为 HyBench 1.9 h、sysbench 7.1 h、YCSB 约 10 h（32 线程下；范围扫描受随机 IO 限制），但两点实测表明每次操作的代价随数据量上升（10 倍数据 1.1–22 倍），SF1000 下原生执行可能达到数十到数百小时。
- **不满足的是随数据量增长的存储**：三来源的 SF1000 静止库为 2.1–12.9 TB，基线 Parquet 0.16–6.6 TB，均超出单机 500 GB；这与管线优化无关，是数据本身的体积（PG 堆与索引、YCSB 每行 1 KB 的随机字段）。在现有机器上，SF100 量级只有 HyBench（静止库约 210 GB）放得下，sysbench（约 490 GB）与 YCSB（约 1.3 TB）放不下。
- YCSB 的一次性阶段（静止库 111 h、首次导出 69 h）在 SF1000 下以天计，主因是散列主键带来的随机 IO 与外部排序。
- 每次回放都要先加载全部基线（SF1000 为 87–312 亿次索引写入），回放实验的时间预算须单独计入。

## 不代表

- 未在大于 SF10 的数据上实测；线性外推不含数据远超内存后的变慢。
- 远程机为共享宿主上的 pod，同一 profile 的原生执行在多次之间相差至多约 1.9 倍（sysbench 631–1,194 s）。
- 两点实测各只有一次运行；HyBench 两点的写入比例不同（SF1 为基线的 3.2 倍），原生代价的比较以同样时长的操作数计。
- YCSB 的 SF10 数字来自 32 线程 new24 重采；其原生时间与 YCSB 8 线程校准不同，SF1000 外推以 32 线程为口径。
